\section{LLM Time Breakdown and Bottleneck Analysis in Agent Tasks}
\label{llm-time-ratio}

\begin{table}[H]
    \vspace{-10pt}
    \centering
    \caption{LLM inference time breakdown across agent tasks.}
    \label{tab:llm_time_breakdown}
    \begin{tabular}{llccc}

        \midrule

        Web Search & Bamboogle       & 49.15 & 32.91 & 66.95\% \\
        Web Search & HotpotQA        & 40.72 & 29.14 & 71.56\% \\
        Coding     & MBPP            & 30.10 & 30.06 & 99.87\% \\
        \bottomrule
    \end{tabular}
\end{table}

\begin{figure}[!b]
    \begin{center}
    \includegraphics[width=1.0\linewidth]{figures/5-time-ratio.pdf}
    \end{center}
    \caption{
        LLM inference time breakdown under different concurrency levels for two agent tasks, Web Search on 2WikiMultihopQA and Coding on MBPP, showing a shift from decode-dominated latency at low concurrency to queue-dominated latency at high concurrency.
    }
    \label{fig:llm_time_ratio}
\end{figure}

We measure the end-to-end execution time and the fraction spent on LLM inference across different agent tasks and datasets, as shown in~\autoref{tab:llm_time_breakdown}.
LLM inference accounts for the majority of the end-to-end latency across all evaluated settings.
For some tasks, the execution time of external tools is negligible, making LLM inference responsible for nearly all of the overall latency.
These results indicate that the end-to-end latency of agent tasks is primarily bottlenecked by LLM inference.
Coding and Web Search tasks typically represent two contrasting cases.
In Coding tasks, the tool execution mainly consists of running generated code and is usually very fast, whereas in Web Search tasks, the agent often needs to retrieve and access multiple webpages, making tool execution more sensitive to network latency.
Despite this difference, LLM inference still accounts for a substantial fraction of the end-to-end latency in both types of tasks.

We further analyze the latency breakdown of LLM requests in agent tasks, as shown in~\autoref{fig:llm_time_ratio}.
The latency of an LLM request mainly consists of three components: prefill, decode, and queueing time.
Existing serving systems have extensively optimized KV-cache reuse, substantially reducing redundant computation during the prefill stage and making prefill latency relatively small.
To preserve KV-cache residency and avoid excessive eviction or recomputation, these systems typically employ admission control based on the number of concurrent requests and the available KV-cache capacity.
When the number of concurrent requests exceeds the capacity that can be supported by the available KV cache, newly arrived requests are queued and can enter inference only after running requests complete and release their KV-cache space.

Based on these results, we observe a concurrency-dependent shift in the LLM inference bottleneck of agent tasks.
At low concurrency, decode time dominates the request latency and serves as the primary performance bottleneck.
As concurrency increases, more requests are blocked by admission control, causing queueing time to grow rapidly and eventually dominate the overall latency.
As a result, the performance bottleneck shifts from decoding at low serving loads to queueing at high serving loads.

\section{Impact of Batch Size on SD Speedup for Agent Tasks}
\label{sd-speedup}

\begin{figure}[H]
    \begin{center}
    \includegraphics[width=1.0\linewidth]{figures/sd_speedup.pdf}
    \end{center}
    \caption{SD speedup under different serving loads, model configurations, and draft lengths. Across both RTX 4090 and A100 GPUs, the benefit of SD generally decreases as batch size increases and can eventually become negative, while the optimal draft length also varies with serving load.}
    \label{fig:sd-speedup}
\end{figure}

To understand how serving load affects the effectiveness of speculative decoding, we measure the SD speedup across different batch sizes, GPU platforms, model configurations, and draft lengths, as shown in~\autoref{fig:sd-speedup}.
Across all evaluated configurations, the benefit of SD consistently decreases as the batch size increases and eventually becomes negative under sufficiently high serving loads.

Our experiments further reveal substantially different SD break-even points across hardware and model configurations.
Specifically, the break-even batch sizes are 36 for 4090-14B-TP2 and 28 for 4090-32B-TP4, compared with 52 for A100-14B-TP1, 40 for A100-32B-TP2, and 64 for A100-70B-TP4.
These results show that the serving load at which SD ceases to provide a performance benefit varies considerably across deployment configurations, highlighting the need to determine when SD should be enabled based on the specific serving environment.

We further observe that the speedup decreases more rapidly on RTX 4090 GPUs than on A100 GPUs.
In particular, A100 GPUs maintain positive SD speedup at larger batch sizes, resulting in a higher break-even batch size between SD and Non-SD execution.
This observation suggests that the effective operating range of SD depends on the underlying hardware capability: more powerful GPUs can sustain the benefit of SD under higher serving loads, whereas less powerful GPUs enter the negative-speedup regime earlier.
Consequently, adaptive SD selection has greater optimization opportunities on resource-constrained GPUs, where choosing between SD and Non-SD execution is more critical as the serving load changes.

Different draft lengths exhibit the same overall trend.
At low batch sizes, more aggressive configurations with longer draft lengths can achieve higher speedup, while increasing the batch size favors more conservative configurations with shorter draft lengths.
This load-dependent behavior motivates existing adaptive SD approaches to adjust the draft length according to the current serving load.
However, draft-length adaptation alone is insufficient at high loads: once the batch size becomes sufficiently large, even the most conservative configuration with a draft length of 1 can incur negative speedup.
Therefore, an effective adaptive SD mechanism should not only adapt the draft length, but also be able to completely disable SD and switch to the native Non-SD execution path when speculative decoding is no longer beneficial.

\textbf{Token Consistency across Adaptive SD Approaches.}
Online inference engines typically employ different execution paths for SD and Non-SD generation to improve efficiency, with different kernels used for key computations such as attention.
As a result, even under deterministic decoding settings (i.e., temperature $=0$ and top-$k=1$), SD and Non-SD execution may generate slightly different token sequences for the same prompt due to differences in their underlying computation paths, although the generated contents are usually semantically similar.
Therefore, token-level consistency provides a practical indicator of whether two execution modes follow the same underlying inference path.
We evaluate this behavior for two adaptive SD approaches, vLLM Dynamic SD and SGLang Adaptive SD, as shown in~\autoref{tab:token_consistency}.
For both vLLM Dynamic SD and SGLang Adaptive SD, when SD is disabled by setting $\text{draft\_len}=0$, the generated tokens are inconsistent with those of the native Non-SD engine but remain consistent with those produced by the native SD engine.
This indicates that setting $\text{draft\_len}=0$ does not fully switch execution back to the native Non-SD path; instead, the engine continues to follow the SD execution path with SD disabled.
In contrast, \sysname's Non-SD mode produces tokens consistent with the native Non-SD engine, while its SD mode remains consistent with the native SD engine.
These results demonstrate that \sysname performs a more complete runtime switch between the native SD and Non-SD execution paths.

\textbf{Non-SD Overhead across Adaptive SD Approaches.}
Since vLLM Dynamic SD and SGLang Adaptive SD continue to execute along the SD path when $\text{draft\_len}=0$, this path is suboptimal for autoregressive Non-SD generation and introduces additional performance overhead.
We therefore measure the Non-SD execution overhead of these two Adaptive SD approaches and \sysname relative to the native Non-SD engine, as shown in~\autoref{fig:nonsd_overhead}.
However, \sysname consistently incurs substantially lower overhead than vLLM Dynamic SD and SGLang Adaptive SD across all batch sizes.
These results further demonstrate the benefit of \sysname's more complete runtime switching between the native SD and Non-SD execution paths.

For the same workload, different workflows exhibit substantially different step distributions; similarly, under the same workflow, changing the workload also leads to noticeable distribution shifts.

Despite using different datasets, the resulting step distributions remain broadly similar, further supporting our observation that the workload--workflow combination is a primary factor shaping the step distribution.

Moreover, we observe a distinctive multimodal pattern for AgentFlow, a multi-step iterative workflow, where agent tasks tend to terminate at only a few specific step counts.

This observation provides an opportunity to predict the remaining steps of an agent task and motivates our prediction method to model step distributions separately for different workflow--workload combinations.

% Type-A 例子介绍
\subsection{Example of Extraction For Type-A Workflows}

The following prompt is taken from an execution trajectory generated by the Plan-and-Solve agent workflow on the SQL task:

\begin{lstlisting}[
    basicstyle=\ttfamily\small,
    breaklines=true,
    escapeinside={(*@}{@*)},
    backgroundcolor=\color{codegray},
    frame=single,
    rulecolor=\color{gray!30},
    framesep=4pt
]
{
  "role": "user",
  "content": "Question: Find the first names that are used for professionals or owners but are not used as dog names."
}
{
  "role": "assistant",
  "content": "### Understanding the Problem:\n"
             "We are asked to find first names that are used for "
             "professionals or owners but are not used as dog names.\n\n"
             "---\n\n"
             "(*@\textcolor{red}{\textbf{\#\#\# Plan:}}@*)\n"
             "(*@\textcolor{red}{\textbf{1.}}@*) Check what tables are available to use.\n"
             "(*@\textcolor{red}{\textbf{2.}}@*) Identify the tables that contain information about "
             "professionals, owners, and dog names.\n"
             "(*@\textcolor{red}{\textbf{3.}}@*) Write a query to extract all unique first names from "
             "the professionals/owners table.\n"
             "(*@\textcolor{red}{\textbf{4.}}@*) Write a query to extract all unique dog names from "
             "the dog names table.\n"
             "(*@\textcolor{red}{\textbf{5.}}@*) Write a query to find the first names that are in the "
             "professionals/owners table but not in the dog names table.
             "(*@{\#\#\# Step-by-Step Execution}@*)"
}
\end{lstlisting}

For this type of agent workflow, the first LLM call generates an explicit plan, which is then included in the context of subsequent LLM calls during task execution. Therefore, the total number of planned steps can be directly extracted from the planning content. Specifically, we locate the \texttt{Plan:} marker and count the numbered items in the plan. In this example, five numbered items are identified, and thus \texttt{num\_plan\_steps} is set to 5.

Since the upper-layer proxy can determine which LLM requests belong to the same Agent Task, the extracted \texttt{num\_plan\_steps} is bound to the corresponding task after it is first obtained. For subsequent LLM requests of the same task, the proxy directly retrieves this value and combines it with the \texttt{cur\_step} carried by the task to estimate the number of remaining steps, without repeatedly parsing the planning content.

\subsection{Example of Extraction For Type-B Workflows}

Unlike Type-A, Type-B workflows do not produce a fixed plan whose
length can be directly extracted. Instead, the proxy determines a
coarse-grained execution state from the latest action and observation
contained in each prompt.

% 总结
For each request, the proxy collects the latest action-related content, including the tool name, sub-goal, command, and observation, and concatenates these fields into a single text representation for state extraction. It then searches this text for the predefined problem-related and positive-completion keywords. Problem keywords are checked first to ensure that failed or abnormal tool executions are identified even when the same content also contains seemingly positive expressions. If no problem keyword is found, the proxy checks for positive keywords that indicate successful execution, sufficient information, or progress toward task completion. When neither type of keyword is detected, the current request is classified as \texttt{neutral}. In this way, each LLM request is mapped to one of the three task-independent states according to the outcome of its latest action.

Since the upper-layer proxy can identify which LLM requests belong to the same Agent Task, it maintains a separate state sequence for each task. After the state of a newly arrived request is extracted, the state is appended to the sequence associated with that task. As the task proceeds through multiple LLM requests and tool executions, the sequence therefore incrementally records its execution progress. For example, a task may produce the following state sequence:
\begin{lstlisting}[
basicstyle=\ttfamily\small,
backgroundcolor=\color{codegray},
frame=single,
rulecolor=\color{gray!30},
framesep=4pt
]
["start", "neutral", "problem", "neutral", "positive"]
\end{lstlisting}
Here, \texttt{start} denotes the initial request, while the subsequent states summarize the outcomes of successive actions. Such a sequence provides a compact representation of the task's execution history without relying on task-specific semantic information.

To estimate the number of remaining steps, the proxy compares the current task state with historical Type-B trajectories from the same workflow and workload. Specifically, it retrieves historical trajectories that reached the same extracted state at the same execution position as the current task. These matched trajectories provide empirical information about how many total steps tasks with similar execution progress typically require. If at least three matching trajectories are available, the proxy examines their endpoints and uses the most frequent endpoint as the estimated total number of steps. Using multiple matched trajectories avoids relying on a single potentially atypical execution.

When fewer than three matching trajectories are available, the proxy falls back to the unconditional step distribution of the same workflow and workload. The remaining steps are then estimated by subtracting the current step from the predicted total number of steps.



% Type-C 例子介绍
\subsection{Example of Extraction For Type-C Workflows}

Unlike Type-B, Type-C workflows follow a fine-grained ReAct pattern,
where LLM requests interleave Thought, Action, and Observation steps.
The proxy considers execution errors, repeated actions, and explicit
task termination, producing five task-independent states:
\texttt{start}, \texttt{normal}, \texttt{error}, \texttt{repeat}, and
\texttt{final\_or\_submit}.

The following examples are taken from ReAct on SQL Task.
In the next prompt, the agent attempts to access a nonexistent table:

\begin{lstlisting}[

\paragraph{Example 5: Final-or-Submit State.}
The following examples are taken from ReAct on SQL Task.
Once the agent determines that the task has been completed, it submits
the result:

\begin{lstlisting}[
basicstyle=\ttfamily\small,

Because the latest action contains \texttt{submit}, the proxy assigns
the state \texttt{final\_or\_submit}. Actions containing
\texttt{final}, or results explicitly marked as completed, are treated

observation, and the preceding action, and assigns the state according
to the following priority:

\begin{lstlisting}[

\end{lstlisting}

The extracted states are incrementally appended to the corresponding
Agent Task, forming sequences such as:

\begin{lstlisting}[
basicstyle=\ttfamily\small,
backgroundcolor=\color{codegray},
frame=single,
rulecolor=\color{gray!30},
framesep=4pt
]
["start", "error", "normal",
"repeat", "normal", "final_or_submit"]
\end{lstlisting}

Unlike Type-B, Type-C additionally conditions prediction on the
transition between the previous and current states. The proxy first
retrieves historical trajectories with the same previous state,
current state, and execution position. If at least three matches are
available, their endpoint distribution is used for prediction.
Otherwise, it falls back to trajectories with the same current state
and execution position, and then to the unconditional step
distribution of the same workflow and workload if necessary. The
median endpoint is used as the estimated total number of steps, from which the current step is subtracted to obtain the remaining-step estimate.

\section{Additional End-to-End Evaluation Metrics}
\label{additional_metrics}

Beyond average JCT, we further evaluate \sysname using additional end-to-end metrics, including P90 and P95 JCT as well as system throughput.
These metrics provide a more comprehensive view of whether the average-JCT improvement of \sysname comes at the cost of tail latency or overall serving efficiency.
The results are shown in~\autoref{fig:p90_p95_throughput}.

\textbf{Tail Latency.}
Since \sysname reduces average JCT by approximating shortest-remaining-time-first scheduling, long-running jobs may receive lower scheduling priority, potentially increasing tail latency.
To examine whether this introduces a long-tail effect, we compare the P90 and P95 JCT across different model and tensor-parallel configurations.
As shown in~\autoref{fig:p90_p95_throughput}, \sysname achieves P90 and P95 JCT comparable to or lower than the baselines, and in several configurations provides noticeable reductions.
This indicates that \sysname reduces average JCT without introducing additional tail-latency degradation.

\textbf{Throughput.}
ThunderAgent's scheduling policy is primarily designed to maximize system throughput, whereas \sysname focuses on reducing average JCT through remaining-step-aware scheduling.
We therefore further evaluate whether this latency improvement comes at the cost of throughput.
As shown in~\autoref{fig:p90_p95_throughput}, \sysname maintains throughput comparable to the baselines across all evaluated configurations.
These results demonstrate that the reduction in average JCT achieved by \sysname does not come at the expense of system throughput.

\section{Experimental Hyperparameters}
\label{app:hyperparameters}

This section summarizes the major hyperparameters and software configurations used in our experiments. Unless otherwise specified, all compared methods use the same workload replay settings, model-generation parameters, and serving configurations under the same hardware setting.

\paragraph{Agent Trace Collection.}
We collect 1,000 execution trajectories from different agent datasets and agent tasks (details in~\autoref{request-and-resource-analysis}). Each trajectory records the input and output of every LLM invocation, together with the corresponding timestamps and complete request and response contents. We split the collected trajectories into training and test sets at a ratio of 5:1. For evaluating remaining-step prediction accuracy, only trajectories in the training set are used to construct the historical profiles, while prediction is performed exclusively on trajectories from the test set. We follow the same separation in the end-to-end experiments, ensuring that no test trajectory is used for profiling and thus avoiding data leakage.

\paragraph{Agent Trace Replay.}
We replay these collected trajectories during evaluation to emulate the execution behavior of real agents without repeatedly invoking the original agent environments. For each trace-driven experiment, we replay 4,096 agent tasks by cyclically reusing trajectories from the test set. The timestamps from the online inference trace are used to determine the task arrival times, with the beginning of the selected trace segment treated as the replay start time. To maintain workload diversity, trajectories from different task categories are interleaved during replay while preserving the temporal characteristics of the original inference trace. For each experimental configuration, all compared methods use the same trajectory sequence and task arrival timestamps. Any randomized components in workload construction use a fixed random seed to avoid performance differences caused by workload sampling.

\paragraph{Inference Engine Configuration.}
The GPU configuration and tensor-parallelism (TP) degree follow the model--hardware configurations described in the main experiments. For all inference engines, we set the GPU memory utilization to 0.85, the maximum model context length to 20,480 tokens, and \texttt{max\_num\_seqs} to 256. Prefix caching and chunked prefill are enabled.

\paragraph{LLM Generation Configuration.}
All LLM requests use a temperature of 0, corresponding to greedy decoding, and the maximum number of generated tokens is set to 1,024. For Qwen models, we additionally disable the built-in thinking mode by setting
\texttt{"chat\_template\_kwargs": \{"enable\_thinking": False\}}.
This setting ensures that the evaluated requests follow the same non-thinking generation mode across experiments.

\paragraph{ThunderAgent Configuration.}
For ThunderAgent, we set both \texttt{metrics-interval} and \texttt{scheduler-interval} to 5.0 seconds. Accordingly, ThunderAgent periodically collects serving statistics and performs scheduling decisions at 5-second intervals.

\paragraph{Speculative Decoding and Switching Configuration.}
We use EAGLE-3~\citep{eagle3} as the speculative decoding method, with a default draft length of 3 unless otherwise specified. For vLLM Dynamic SD and SGLang Adaptive SD, the switching threshold \(T\) is determined separately for each model--hardware configuration from the profiling results in~\autoref{sd-speedup}. SD is enabled with a draft length of 3 when the running batch size is at or below \(T\), and disabled by setting the draft length to 0 when the batch size exceeds \(T\):
\[
[1,T]\rightarrow 3,\qquad [T+1,256]\rightarrow 0.
\]
Here, \(T\) denotes the profiled SD break-even threshold. \sysname uses the same profiled threshold to determine when to switch directly between its native SD and non-SD execution paths. The thresholds for individual configurations are reported in~\autoref{sd-speedup}.
